# Golden Capsule guest-protocol files (C-05)

These files pin what crosses the host / guest boundary of a Capsule in the current Python
implementation, so the Rust host can prove specification C-05: it must keep working with images
whose guest runtime is the Python PyInstaller bundle, and `python-pyinstaller` runtime bundle
manifests stay byte-identical and omit the new runtime kind field.

Everything here is generated by `scripts/golden/export_capsule.py`. Do not edit the generated
files by hand. Edit the exporter and regenerate them instead.

```sh
python scripts/golden/export_capsule.py --write   # regenerate (Linux only)
python scripts/golden/export_capsule.py --check   # exit 1 and name each drifting file
```

## Layout

| Path | Written by | Contract |
|---|---|---|
| `runtime-bundle/argus-guest-runtime.zip` | `create_guest_runtime_bundle` from a two-file TEST ONLY payload (`argus-guest-runtime-bundle-v1`, Windows 11 x86_64) | C-05 bundle format |
| `runtime-bundle/argus-runtime-manifest.json` | the manifest exactly as stored inside the ZIP | C-05 manifest bytes (no `runtime_kind`) |
| `bootstrap/bootstrap.json`, `bootstrap.token`, `tls-cert.pem` | `create_bootstrap_attempt` (`argus-bootstrap-v1`); the token is TEST ONLY | C-05 bootstrap medium |
| `control/host/cap-<id>.json` | `CapsuleControlRegistry` after two reserved generations, a commit and the move to `active` (`argus-capsule-control-v1`) | C-05 host control record |
| `control/guest/control.json` | `GuestControlStateStore.commit_generation` (`argus-guest-control-v1`) | C-05 guest control state |
| `expected/runtime-bundle.json` | build result, ZIP members (names, fixed 1980-01-01 timestamps, modes), `verify_guest_runtime_bundle` and its rejections (wrong outer digest, wrong runtime version or OS, a payload member changed without the manifest), and `GuestRuntimeBundleManifest.from_mapping` on the manifest as written, with `runtime_kind` (`native` and `python-pyinstaller`, both rejected by the Python line, as C-05 expects) and with an unsupported format version | C-05 |
| `expected/bootstrap.json` | `load_bootstrap_manifest` on the attempt and on changed copies (certificate digest, unknown field, schema v2, generation 0, a token path, missing `created_at`) | C-05 |
| `expected/control.json` | reserved generations, the committed and active records, a stale commit, a replayed guest generation, and `from_mapping` on the records as written and changed | C-05 |
| `_manifest.json` | file list and hashes, Python source hashes, and in `generated_with` the git commit, package version and Python version (`--check` ignores `generated_with`) | all |

### The bootstrap certificate is reused, and the private key is not kept

The bootstrap TLS certificate is signed with ECDSA, which is randomized, so it cannot be
reproduced. It was made once by the real `_certificate_identity`; afterwards the exporter
returns the committed `bootstrap/tls-cert.pem` from that function instead of signing a new one.
Everything else in the attempt is still written by `create_bootstrap_attempt`. Generating a new
certificate does not change anything else in the export (the exporter restores its clock and
counters around it). To make a new one, delete `bootstrap/tls-cert.pem` and run `--write`.

The certificate's private key is **not** exported: `load_bootstrap_manifest` checks only the
certificate, and the attempt writes a TEST ONLY placeholder in its place.

## Determinism and environment

Same scrubbed child process and deterministic patches as `tests/golden/ates`
(`scripts/golden/_harness.py`). The guest runtime payload is two small TEST ONLY files, not a
real PyInstaller build.
